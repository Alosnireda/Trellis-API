# Signed Audit Receipts for Privileged Actions

This document specifies the signed audit receipt architecture for privileged operations in Trellis API.

## Overview & Architecture

Privileged and sensitive actions (role assignments, user suspensions, withdrawal authorizations, emergency pause toggles, audit exports) are recorded in the append-only `sensitive_action_events` table with monotonic sequences and SHA-256 hash chains.

Signed audit receipts provide exportable, tamper-evident cryptographic proofs that an action was executed by an authorized actor and committed to the immutable audit ledger.

### Receipt Components

1. **Receipt Document (`PrivilegedActionReceipt`)**:
   - `schema`: `"trellis/privileged-action-receipt/v1"`
   - `receiptId`: Deterministic unique identifier (`rcpt_<hash_prefix>`)
   - `eventId`, `sequence`: Exact audit ledger identity
   - `action`, `scope`: Specific sensitive action category
   - `actorId`, `actorType`, `actorRole`: Complete caller attribution
   - `resourceType`, `resourceId`: Target entity identity
   - `reason`: Mandatory operational justification
   - `status`: Execution outcome (`succeeded` or `failed`)
   - `eventHash`, `previousHash`: Immutable hash-chain linkage
   - `occurredAt`, `issuedAt`: Canonical UTC ISO timestamps

2. **Integrity Block (`PrivilegedReceiptIntegrity`)**:
   - `receiptHash`: SHA-256 digest of `canonicalJson(receipt)`
   - `signature`: HMAC-SHA256 signature generated by `ExportSigningService`
   - `signingAlgorithm`: `"HMAC-SHA256"`

## Verification Workflow

Verification executes two independent checks:
1. **Document Canonical Integrity**: The receipt is serialized with `canonicalJson` (lexicographically sorted keys, strict numeric bounds, no whitespace) and hashed. If the recomputed hash does not match `integrity.receiptHash`, the receipt has been modified.
2. **Cryptographic Authenticity**: The signature is verified against `receiptHash` using the system audit signing key with timing-safe comparison (`timingSafeEqual`).

## Operational Paths & Edge Cases

| Path / Condition | Handling |
| :--- | :--- |
| **Normal Path** | `GET /audit-trail/sensitive-actions/:id/receipt` returns 200 with the receipt document and integrity block. |
| **Verification Path** | `POST /audit-trail/sensitive-actions/receipt/verify` validates both hash and signature and returns `{ valid: true, errors: [] }`. |
| **Tampered Field** | If any property (actor, reason, status) is altered, hash recomputation fails with `Receipt hash mismatch`. |
| **Forged Signature** | If signature does not match key, returns `Cryptographic signature validation failed`. |
| **Non-Terminal Action** | Receipts can only be issued for terminal outcomes (`succeeded` or `failed`). Non-terminal events throw `BadRequestException`. |
| **Missing Chain Head** | If the underlying event lacks an `eventHash`, receipt generation fails safely with `BadRequestException`. |
| **Key Rotation** | Future key rotation uses schema versions (`v1`, `v2`) or key identifiers without breaking existing stored receipts. |

## Contract Preservation

This implementation is backwards-compatible:
- Existing `SensitiveActionEvent` entity and table columns remain unchanged.
- New endpoints and services are purely additive.
- Role/permission guards (`JwtAuthGuard`, `ComplianceOfficerGuard`) maintain strict authorization boundaries.
